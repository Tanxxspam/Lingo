## 2. Component Breakdown

### 2.1 Frontend (React)
- **CheckoutPage** — simulated product checkout. Captures three signal types and posts them to the backend as they occur: idle timer, `popstate` (back button), OTP field failure.
- **ConciergeWidget** — chat-style panel that renders whatever message/offer the backend returns. Two buttons: Accept, Dismiss. The response is posted back to `/api/agent/intervene` as an outcome.
- **MetricsDashboard** — pulls from `/api/metrics/summary` and renders aggregate charts (baseline vs. recovered conversion, revenue recovered, intervention-type breakdown).
- **Batch Simulate control** — triggers the backend to generate N synthetic sessions with randomized hesitation patterns, so results can be shown at scale rather than one session at a time.

### 2.2 Backend (FastAPI)
- **Session service** — creates a checkout session tied to a Razorpay test-mode order.
- **Event ingestion** — receives hesitation signals, timestamps them, appends to the session's event log.
- **Rules engine** — the core decision-making component (see Section 3). Pure Python, no LLM involvement in the actual decision of *whether* and *what* to offer.
- **Agent messaging** — a thin wrapper around the Claude API that takes the rules engine's decision (e.g. `{"type": "discount", "value": "10%"}`) and turns it into a natural, on-brand sentence. This call never decides money amounts — it only phrases them.
- **Razorpay client** — wraps Orders API and Payment Links API calls in test mode, and exposes available payment methods (UPI, card, netbanking, EMI-on-card) for the rules engine to reference.
- **Metrics service** — aggregates events, interventions, and outcomes into the dashboard's summary numbers.

### 2.3 Data Layer (SQLite)
Four tables form the audit trail:
- `sessions` — one row per checkout session (order id, amount, status, created_at)
- `events` — hesitation signals as they occur (session_id, type, timestamp)
- `interventions` — every offer made (session_id, type, value, reason, timestamp)
- `outcomes` — accept/reject/no-response per intervention, and whether the session ultimately converted

Every row in `interventions` includes a `reason` string generated by the rules engine (e.g. `"idle_time > 20s AND no_prior_intervention"`), which is what makes the system's decisions explainable after the fact.

## 3. Decision Flow (Sequence)

1. Frontend detects a signal → `POST /api/checkout/event`
2. Backend appends the event, then calls the rules engine with the session's full event history
3. Rules engine evaluates conditions against stopping rules (see below) and either:
   - Returns `no_action`, or
   - Returns a decision object: `{type, value, reason}`
4. If a decision is returned, backend calls Claude API with the decision object to generate the customer-facing message
5. Backend logs the intervention, returns the message to the frontend
6. Frontend displays it in the Concierge Widget
7. User's response (accept/reject) is posted to `/api/agent/intervene`, logged as an outcome
8. Metrics service recalculates aggregate stats on each outcome write

## 4. Stopping Rules (Safety / Bounding)

These are hardcoded, not configurable by the LLM layer:

- **Max interventions per session:** 2
- **Cooldown between interventions:** 15 seconds minimum
- **Max discount offer:** capped at a fixed % (e.g. 15%), never chosen dynamically by the LLM
- **EMI/payment-method offers:** limited to methods actually available on the order via the Razorpay API — no offer is shown that couldn't actually be fulfilled
- **No repeat offers:** if a discount was rejected once, the session will not be offered a second discount — it escalates to a different intervention type instead

## 5. Why Rules Engine + LLM Are Separated

Money-affecting decisions (whether to discount, how much, which payment method to suggest) are handled by deterministic, inspectable Python logic. The LLM is used exclusively for natural-language generation of the already-decided offer. This keeps every action:
- **Explainable** — each decision has a logged reason string
- **Bounded** — hard caps enforced in code, not prompted
- **Gated** — stopping rules prevent runaway or repeated interventions

This separation is the direct answer to the Buildathon's requirement that *"every money action [be] explainable, bounded and gated."*
